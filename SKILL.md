# Sonar: разбор замечаний по модулям

**Язык: только русский.** Все сообщения, пояснения, предупреждения, вопросы и варианты `question` пользователю — на русском, включая первый ответ и ошибки. Технические идентификаторы, команды и имена файлов не переводить.

## СТОП после ссылки: ожидание JSON (приоритетное правило)

Эти правила обязательны и имеют приоритет над дальнейшими шагами навыка.

1. Если пользователь передал URL страницы SonarQube для новой выгрузки, выполни ровно один локальный вызов `python scripts/sonar_index.py api-url "<исходный URL>"`. Он только преобразует строку, без сети. После получения URL никакие предварительные проверки и другие инструменты не нужны; `route` выполняется при запуске команды, а не повторно перед формированием ссылки.
2. Покажи готовую API-ссылку и попроси: «Откройте ссылку в браузере, скопируйте весь JSON и вставьте его следующим сообщением в чат».
3. `WAITING_FOR_USER_JSON` в выводе означает: немедленно заверши текущий ответ обычным финальным сообщением. После вызова `api-url` не вызывай НИКАКИХ инструментов до следующего сообщения пользователя: ни `question`, ни shell, ни чтение файлов, ни планировщик задач. Не продолжай работу в фоне и не объединяй `api-url` с другими командами. Если локальное формирование ссылки завершилось ошибкой, сообщи об ошибке и попроси исправленный URL; также остановись без повторного вызова.
4. Следующее сообщение разрешает продолжение только по его содержанию. Если пользователь вставил JSON, сразу выполни этап 2: скрипт извлечёт текст из текущей сессии. Не ищи локальный файл, не переписывай JSON. Если JSON ещё нет, продолжай ожидать. До получения JSON запрещены проверки Git, репозиториев, веток, зависимостей и BSL-кода.

**Самостоятельное обращение к SonarQube категорически запрещено на всех этапах**, даже если агент уверен, что сервер доступен. Нельзя скачивать JSON, проверять доступность сервера или открывать URL через `curl`, `Invoke-WebRequest`, `Invoke-RestMethod`, Python HTTP-библиотеки, `webfetch`, браузерные инструменты, MCP, другие программы или делегирование. Не делай сетевых попыток и не повторяй их при ошибках или тайм-аутах. URL открывает только пользователь в своём браузере.

Аргумент команды: $ARGUMENTS

При запуске `/sonar` первое действие — только эта команда, до чтения состояния и до вопросов (если URL уже передан для новой выгрузки, действует приоритетное правило выше):

`python scripts/sonar_state.py route --arg "$ARGUMENTS"`

Дальше строго `mode` из ответа. Пустой аргумент — это `new`, не `resume`.

- `new` — новый разбор. Не вызывай `resume`. Не удаляй и не перезаписывай старые отчёты.
- `resume` — только незавершённый разбор. Если таких нет, скажи об этом и остановись. Новый разбор не начинай.
- `skipped` — пересмотр ранее пропущенных. Новую выгрузку не требуй, если старый JSON на месте.
- `unknown` — спроси, что имелось в виду. Сам режим не выбирай.
- `pace=detailed` — по одному вопросу. Иначе быстрый режим.

Сам разбор не начинай, пока пользователь не вызвал `/sonar`, `/sonar resume`, `/sonar skipped` или `/sonar detailed`.

OpenCode не ходит в SonarQube. Пользователь открывает ссылку и передаёт JSON.
Не проси пароли, токены и cookie. Не ставь зависимости. Не запускай BSLLS, Sonar Scanner и Java.
Без отдельного разрешения запрещены `git commit`, `push`, `checkout`, смена ветки и сброс изменений.

Все скрипты — стандартная библиотека Python. Пути `scripts/...` считай относительно каталога этого скилла, а не рабочего репозитория; при shell-вызове укажи `workdir` каталога скилла или абсолютный путь скрипта. Весь JSON, экспорт сессии, индекс и состояние в контекст не копируй. Читай компактный вывод.

Если текст этого навыка уже доступен в контексте команды, повторно вызывай `skill` только при утрате необходимых инструкций. Явный вызов `/sonar` по-прежнему обязателен.

## Запрет самостоятельных решений

Пока пользователь не ответил в `question`, запрещено пропускать, исправлять, откладывать и переносить старое решение. Уверенность, что замечание ложное, мелкое или появилось из прошлой правки, ничего не разрешает.

`decide` и `carry` вызывай только с `--answered` и только после ответа `question` в этом ходе. `applied` — ещё и `--allow-applied`, и только после правки файла.

Новое замечание, особенно `BUG` и `VULNERABILITY`, не считай дефектом без кода и не закрывай без выбора пользователя. Рекомендацию давай, действие не выполняй.

Не объединяй независимые замечания в одно решение без отдельного вопроса. Однотипные можно спросить одним вопросом, если им правда подходит одно действие, и в вопросе перечислить все места.

## Зависимости

Для BSL точнее, если уже есть `bsl-sonar-rules`, `bsl-code-review` и MCP `rlm-tools-bsl`. В начале BSL-разбора проверь один раз. Если чего-то нет, предупреди и продолжай. Не устанавливай сам.
`RULES.md` читай один раз на разбор. Фрагмент модуля перечитывай только если код изменился.

Без MCP читай нужный фрагмент. Без каталога правил не выдумывай формулировки: сообщение Sonar и код.

Инструкции необязательных зависимостей не отменяют запрет запуска BSL Language Server, Sonar Scanner и Java. Оформление доработок и авторских комментариев определяют инструкции текущего проекта разработчика; собственный формат маркеров навык не навязывает.

## Новый разбор

Спроси страницу замечаний, если ссылки нет. Сам URL не открывай.

### Этап 1. Сформировать ссылку и остановиться

Получив URL, выполни ровно один локальный вызов, без других команд в этом вызове:

`python scripts/sonar_index.py api-url "<исходный URL>"`

Вывод: первая строка — API-ссылка, вторая — `WAITING_FOR_USER_JSON`. Скрипт сохраняет фильтры, меняет `id` на `componentKeys`, ставит `ps` не больше 100 и по умолчанию `p=1`.

Далее выполни приоритетное правило «СТОП после ссылки» в начале: покажи ссылку, попроси вставить JSON текстом и заверши ответ. Не повторяй `route`, не вызывай другие инструменты.

Нельзя самостоятельно обращаться к SonarQube через `curl`, `Invoke-WebRequest`, Python HTTP-библиотеки или любые другие средства, даже при наличии доступа. Нельзя повторять сетевые попытки после ошибок и тайм-аутов. До получения JSON не проверяй Git, репозитории, зависимости и BSL-код.

### Этап 2. Пользователь вставил JSON в чат

Первое действие — **один** локальный вызов:

`python scripts/sonar_ingest.py --call-id <новая-уникальная-метка>`

Метка — придуманные тобой 24–64 шестнадцатеричных символа, каждый вызов новая; для её генерации отдельная команда не нужна. Не передавай JSON, URL, session ID или путь к выгрузке аргументами. Скрипт находит именно выполняемый shell-вызов в локальной истории OpenCode, получает его session ID, последнее пользовательское сообщение и предшествующую выдачу API-ссылки. Сам проверяет JSON, проект, PR, страницы, сохраняет исходный текст в `~/.config/opencode/sonar-reports/`, строит индекс существующим индексатором и создаёт состояние. Сохранённые решения не перезаписывает.

- `READY` — обработка завершена. Используй `issuesPath`, `indexPath`, `statePath` из результата. Сразу покажи короткую сводку `total`, `severities`, `modules` и переходи к проверке репозитория и обычному разбору. Повторные `index`/`stats`, чтение исходного JSON и вопрос «начинаем?» не нужны.
- `WAITING_FOR_USER_JSON` — покажи только недостающие API-ссылки из `urls`, попроси вставить JSON каждой страницы отдельным сообщением и заверши ответ. Скрипт соберёт страницы этой сессии; до полной выгрузки разбор не начинается.
- `ERROR` — один понятный ответ по полю `message` и остановка. При ошибке JSON попроси вставить полный JSON повторно. При недоступности локальной истории сообщи конкретное ограничение. Не повторяй вызов с другим синтаксисом, не ищи файлы и не выбирай другую сессию.

**Не проси сохранить файл, указать путь или загрузить вложение.** Не создавай JSON через `echo`, here-string, PowerShell, `python -c` или ручное копирование моделью. Не выгружай историю в текстовый вывод инструмента. Не читай БД, полный экспорт или индекс вручную после успешного приёма. Подробности реализации и ограничения — в `README.md`.

Компактно определи корень репозитория, текущую ветку, HEAD и состояние рабочего дерева. Не выводи полный `git show-ref` или все ветки без необходимости; запрашивай только конкретные refs. Целевую ветку PR определяй по подтверждённым данным, не угадывай как `develop`; сохраняй проверяемое основание выбора. Если достоверных данных нет, спроси пользователя. Состав задачи — `git diff <целевая>...HEAD` и незакоммиченный diff. При явном расхождении ключа Sonar и репозитория остановись и спроси. Ветку не меняй.

Состояние уже создано в каталоге отчётов, путь вернул скрипт. После локальной проверки запиши подтверждённые значения командой `python scripts/sonar_state.py set-context <state.json> --repo "<абсолютный путь>" --branch "<ветка>" --target-branch "<целевая ветка>" --target-evidence "<основание>" --pace fast|detailed`; остальные поля и решения сохраняются. Перед любыми изменениями кода заново сверь рабочий репозиторий и Git-ветку с этими данными; при расхождении остановись и спроси. После правки проверь состояние Git; при возобновлении также проверь репозиторий и ветку. Не повторяй известные пути и подробности Git в служебном выводе без необходимости.

BSL-зависимости и правила загружай только перед разбором первого BSL-модуля. Предварительный анализ всех модулей не выполняй.

### Повторный анализ

Перед опросом найди прежние состояния:

`python scripts/sonar_state.py find --reports "<каталог sonar-reports>" --match "<pr-N или ключ проекта>"`

Исключи текущий `statePath`, созданный приёмом, из прежних состояний; сравнивай только тот же проект и PR/ветку. Повторный запуск приёма сам по себе не повод снова спрашивать о переносе решений.

Если подходящего нет, опрашивай всё как новое.

Если есть, сравни, не копируя решения:

`python scripts/sonar_state.py compare <старое-состояние> --issues <новый.json> --old-issues <старый.json> --compact`

`--old-issues` передавай, только если старый JSON есть. Покажи число исчезнувших, сохранившихся и новых. `appliedStillOpen` — замечание осталось в Sonar, старый статус «исправлено» не подтверждён. `unstable` — ключ совпал, а правило или файл нет; такое решение не переносить.

Затем один `question` с тремя вариантами. До ответа `carry` не вызывай.

- Оставить прежние решения (рекомендуется) — перенести только явно подтверждённые по ключу `skipped`, `deferred` и `agreed`. Новые и `appliedStillOpen` разобрать заново.
- Пересмотреть выборочно — спросить модуль, правило или группу и повторно спросить только их. Остальные подтверждённые пропуски оставить.
- Пересмотреть все — заново спросить все сохранившиеся пропуски. Прежние решения не удалять.

Перенос только после ответа:

`python scripts/sonar_state.py carry <старое> --to <новое> --issues <новый.json> --strategy keep|selected|review-all --answered`

Для `selected` добавь `--module` или `--rule` тех групп, которые нужно спросить снова. Старый файл не удаляется. История пересмотра пишется в `history`.

## Быстрый и подробный режим

По умолчанию быстрый. Подробный — при `pace=detailed` или если пользователь просит «подробно».

В обоих режимах у каждого вопроса есть объяснение, рекомендация и выбор. Экономия токенов не отменяет чтение кода.

Быстрый режим:

- контекст модуля читай один раз;
- для небольшого BSL-модуля с замечаниями по всему файлу предпочитай одно чтение вместо перекрывающихся; для большого — целые затронутые методы и необходимые зависимости;
- конкретный метод сначала ищи по точному имени, не объединяя поиск с широкими выражениями; при изменении кода или утрате контекста повторное чтение допустимо;
- связанные замечания одной правки — один вопрос;
- однотипные с одним подходящим решением — один вопрос, места перечисли;
- независимые вопросы передавай одним вызовом `question`, по 5–8; если больше, следующая партия;
- после партии не повторяй сводку, прочитанный код и длинные объяснения.

Подробный режим — один вопрос на один вызов `question`.

## Опрос модуля

Порядок: модуль, функция или процедура, строка. Его даёт `sonar_index.py order`. По серьёзности не сортируй. Серьёзность показывай в вопросе.

Очередь модуля бери так, без полного индекса в чат:

`python scripts/sonar_state.py queue <state.json> --index <index.json> --limit 8`

Код до конца опроса модуля не меняй. Между вопросами BSL не правь.

`question` обязателен. Не пиши «выбери А, Б, В или Г». Текст вопроса самодостаточен.

В каждом вопросе: понятное название; модуль; функция или процедура, если она есть в коде; строка или диапазон; претензия Sonar; стиль это или возможный дефект поведения; рекомендация. Короткий фрагмент — только если без него выбор непонятен.

Рекомендуемый вариант первый, с пометкой «(рекомендуется)». Не показывай вариант, которого нет. Подписи: «Исправить минимально», «Альтернативное исправление» только если оно полезно, «Пропустить», «Отложить».

Сразу после ответа:

`python scripts/sonar_state.py decide <state.json> --key <key> --choice <choice> --status agreed|skipped|deferred --note "<кратко>" --answered`

`agreed` — согласился, код ещё не менялся. `skipped` и `deferred` код не меняют. Длинные `key` пользователю не показывай.

`CognitiveComplexity` и `CyclomaticComplexity` в старом коде не исправляй только ради метрики. Рефакторинг предлагай отдельно и не делай без согласия.

Если `question` недоступен, тот же выбор текстом. Несколько вопросов одним вызовом поддерживаются: аргумент `questions` — массив.

## Пакетное исправление

Когда у модуля не осталось замечаний без решения:

- проверь, что согласованные правки не конфликтуют; при конфликте спроси, сам не выбирай;
- одним проходом внеси только согласованное;
- перед правкой сверь замечание с текущим BSL; если код уже другой, не применяй старое решение и спроси снова;
- пропущенное и отложенное не меняй;
- для BSL проверь доступными `bsl-sonar-rules` и `bsl-code-review`;
- покажи один короткий diff модуля, не diff каждого замечания;
- отметь `applied` только после правки, с `--answered --allow-applied`;
- итог модуля: рассмотрено, исправлено, пропущено, отложено, файлы, проблемы;
- переходи к следующему модулю.

Коммит не создавай.

## `/sonar resume`

`python scripts/sonar_state.py find --reports "<sonar-reports>" --mode resume`

Несколько незавершённых — спроси, какое. Ни одного — так и скажи, новый разбор не начинай.

Дальше `resume <state.json>`: компактная сводка, не весь JSON. Сначала доопроси модуль, затем пакетная правка, если опрос уже закончен.

## `/sonar skipped`

1. `find --mode skipped`. Несколько разборов — спроси. Один подходящий — возьми его. Новую выгрузку не требуй, если в состоянии есть путь к JSON или JSON лежит рядом.
2. `skipped <state.json> --issues <json>` — покажи число и группы по модулю и правилу, не весь список.
3. `question`: модуль, правило или все пропущенные.
4. Повторно спрашивай только выбранные. Новое решение пиши через `decide --answered`: прежнее останется в `history`.
5. После решений модуля — пакетная правка по обычным правилам. Перед правкой сверь код. Если строка или фрагмент уже не те, решение не применяй и спроси снова.

## Итог

В конце или по запросу: всего, рассмотрено, исправлено локально, пропущено, отложено, без решения, файлы и какие проверки выполнены. `complete` ставь в состоянии только когда не осталось открытых и отложенных. Исчезновение в Sonar утверждай только по новой выгрузке, не по локальной правке.

Итоговый Markdown — один раз в конце или по запросу. Во время опроса большой Markdown не переписывай.
